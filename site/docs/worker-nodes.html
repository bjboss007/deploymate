Operate

Worker nodes

A small server doesn't have to run everything. Add another computer, yours or a friend's, as a worker node, and run a whole project on it: its apps and its databases together. DeployMate still builds, routes and monitors from your server; the containers run on the node. Use it for something heavy (a machine-learning model, video processing) or just to get more memory than your server has.

A node sees everything that runs on itIts owner can read the code, environment variables and data of what you place there. Only add machines whose owner you trust.

What you need

The nodeAny Linux machine you can reach over SSH: a friend's PC, a mini PC, another VPS. It can have a different CPU type from your server.
A private routeTailscale on both machines (free for personal use) is the easy way: each gets a private 100.x.x.x address that works from anywhere. A shared home or office network works too. Nothing on the node is opened to the internet.
On the nodeDocker, and a user that may run it.

1. Prepare the node

On the node, as a user with sudo. Skip what is already there.

curl -fsSL https://get.docker.com | sudo sh
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up

# a user DeployMate will log in as, allowed to run Docker
sudo adduser --disabled-password --gecos "" dmnode
sudo usermod -aG docker dmnode

Note the node's Tailscale address (tailscale ip -4). Install Tailscale on your DeployMate server the same way and sign in to the same account.

2. Add it in DeployMate

  1. Open Nodes in the sidebar and press Create this server's key. It shows a public key.
  2. On the node, add that key to the user from step 1:
sudo -u dmnode mkdir -p -m 700 /home/dmnode/.ssh
echo 'PASTE THE PUBLIC KEY HERE' | sudo -u dmnode tee -a /home/dmnode/.ssh/authorized_keys
sudo chmod 600 /home/dmnode/.ssh/authorized_keys
  1. Back in DeployMate, enter a name (say friend-pc) and the address ssh://dmnode@100.64.0.5 (the user, then the node's address; add :2222 for a different SSH port), then press Add node.

DeployMate connects straight away and shows the node's CPUs, memory and Docker version, or the reason it couldn't. Reach the machine through an SSH alias or a tunnel instead of a plain address? Then also fill in address for its ports: the private address its apps will be reached at.

A node is checked every minute and shows offline after three failed checks in a row. It returns to ready by itself when it answers again.

3. Choose where a project runs

Open the project and, under Where it runs, pick the node. Do this before adding anything: a project that already has a database or a deploy stays where it is, because its apps and databases must share one machine's network. To use a node for existing work, create a new project on it.

From then on, deploys, databases, logs, metrics, backups and restarts of that project work as usual and happen on the node. The preview address and your domains reach it through your server, so DNS stays pointed at the server.

Taking a node out of use

  • Drain stops anything new from being placed on it. Use it before you need the machine yourself; what already runs there keeps running.
  • Remove works only when no project uses the node. Removing a node never deletes anything on the machine.

If it won't connect

The Nodes page shows the reason. The usual ones:

It saysWhat to do
Permission denied (publickey)The key from step 2 is not in that user's ~/.ssh/authorized_keys, or the file's permissions are too open (chmod 600).
Permission denied … dockerThe user isn't allowed to use Docker. Run sudo usermod -aG docker dmnode on the node, then try again.
Connection timed out, no route to hostTailscale is down on one of the machines, or they are signed in to different accounts. Check tailscale status on both.
Host key verification failedThe node was reinstalled, so its SSH identity changed. If that is expected, remove the old line for it from the known_hosts of the user that runs DeployMate.

GPUs

An app can use the node's NVIDIA graphics cards, for example to serve a language model. This works on a Linux machine with an NVIDIA card. Docker on a Mac or Windows laptop cannot pass a GPU to containers, and AMD or Intel cards are not supported yet.

1. Install the GPU support on the node

Install the NVIDIA driver first (nvidia-smi should print your card), then:

curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
  | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# the test
docker run --rm --gpus all ubuntu nvidia-smi

The last command must print the same table as nvidia-smi. Then press Check on the node in DeployMate: the node's line now shows the card and its memory, such as NVIDIA GeForce RTX 4090 24 GB.

2. Switch it on for the app

Put the project on the GPU node (step 3 above), then on the app's page tick Use the machine's GPUs and press Save. It applies from the next deploy. If the node has no GPU support, DeployMate says so instead of saving; if a deploy asks for a GPU on a machine that has none, it fails with the reason and what to install.

An app gets all the GPUs on its machine. GPU memory is not shared out between apps: two apps on one card compete for its memory.

Example: your own AI model server

  1. Create a project on the GPU node and an app in it. Set its image to ollama/ollama and its port to 11434, turn on the GPU, and add /root/.ollama under Persistent folders so downloaded models are kept.
  2. Deploy, add a domain, then load a model with curl https://your-domain/api/pull -d '{"model":"llama3.1"}'.

Persistent folders are described in How it fits together; the short version: they live on the node, survive redeploys and are kept if you delete the app. They are not part of backups yet.

Good to know

  • Images travel to the node. The build runs on your server (or on a build machine) and the image is sent over. A multi-gigabyte image takes a while over a home connection. If the node has a different CPU type from where the image was built, the node downloads its own copy instead.
  • Ports stay private. What an app publishes on the node is bound to the node's private address, not to its public interface.
  • A drained or offline node blocks deploys to it, including redeploying something that already runs there. Nothing quietly falls back to your server.
  • Not yet: moving a project between machines, picking a node by free GPU automatically, jobs that run to completion, spreading one project over several machines, and picking a node automatically.
